# Task 3 report — RomM client (auth + platform resolution)

## Update: contract-verified fixes (post-review)

The coordinator checked my guessed field names/encodings against RomM
4.9.2's live `openapi.json` on an LXC container and sent back corrections. Fixed in
commit `822ca16` on this same branch:

1. **`POST /api/collections` is `multipart/form-data`, not JSON** (my
   original guess). `Body_add_collection_api_collections_post` mixes
   `Form` fields (`name`, `description`, `url_cover`) with an optional
   `artwork: binary` file, which is what makes FastAPI require multipart
   even with no file attached. httpx only switches to multipart encoding
   when a `files=` mapping is given (verified directly: `data=` alone, or
   with `files={}`/`files=[]`, always produces
   `application/x-www-form-urlencoded` — confirmed by reading
   `httpx._content.encode_request`, which checks `elif files:` before
   falling through to urlencoded). `ensure_collection()` now sends
   `data={"name", "description": "", "url_cover": ""}` plus
   `files={"artwork": ("", b"", "application/octet-stream")}` — an empty
   file part, mirroring what a browser sends for an unselected HTML file
   input, which is the only way to force multipart without an actual file
   to attach.
2. **`POST /api/collections/{id}/roms` is JSON** (`CollectionRomsPayload`,
   `{"rom_ids": [...]}`) — my original guess was already correct; added a
   test asserting `content-type: application/json` to pin it down.
3. **`platform_id()` now falls back to `fs_slug`** when `slug` doesn't
   match, and the lookup is case-insensitive (both keys are cached
   lowercased). Previously it only ever preferred `slug` over `fs_slug`
   via `or`, so an fs_slug-only match or a differently-cased slug would
   have raised `RommError` incorrectly — the wrong-platform failure mode
   the coordinator flagged as worse than a visible error.
4. **Any 401/403 from `_authorized_request`** (not just the token
   endpoint) now raises a `RommError` whose message plainly contains
   "authentication/authorization failed" rather than a generic
   `"{method} {path} failed (403): ..."`. Added a test hitting
   `add_to_collection` with a mocked 403 and asserting the message matches
   `(?i)authoriz` and is not an `httpx.HTTPStatusError`.
5. `grant_type` was already sent explicitly on `/api/token` — no change
   needed there.

**Scope note (raised, not silently handled):** `Body_token_api_token_post`
has a `scope` field defaulting to `""`. RomM may require an explicit scope
for write operations like upload; I did not guess one — sending a wrong
guessed scope could be a worse failure mode than the documented default,
and it would only surface at the first real write (e.g. Task 4's chunked
upload). This needs to be checked against the live server at Task 8's
live end-to-end run. If it turns out a scope is required, the fix is
localized to `RommClient.authenticate()`'s `data` dict.

## What changed

- **New:** `src/romm_hub/romm/__init__.py` — package docstring only.
- **New:** `src/romm_hub/romm/client.py` — `RommClient` and `RommError`.
  - `RommClient(base_url, username, password, timeout=30.0, transport=None)`
    — `transport` is the injectable `httpx.BaseTransport` the plan asked
    for, so tests never touch the network.
  - `.authenticate()` — `POST /api/token` as `application/x-www-form-urlencoded`
    (OAuth2 password grant body: `grant_type`, `username`, `password`), reads
    `access_token` from the JSON response, caches it as the bearer token.
    Lazily invoked by any authorized call if no token is cached yet.
  - `.list_platforms()` — `GET /api/platforms` -> `list[dict]`.
  - `.platform_id(slug) -> int` — fetches and caches the *entire* platform
    listing on first use (keyed by `slug`/`fs_slug` -> `id`), so resolving
    any number of slugs afterward costs zero further HTTP requests. Raises
    `RommError` naming the slug if it isn't in the listing.
  - `.list_roms(platform_id) -> list[dict]` — `GET /api/roms?platform_ids=...`.
  - `.list_collections()`, `.ensure_collection(name) -> int` (looks up by
    name, creates via `POST /api/collections` if absent), and
    `.add_to_collection(collection_id, rom_ids)` (`POST
    /api/collections/{id}/roms`) — the two interfaces the plan lists that
    Step 1 doesn't explicitly mandate tests for; I covered them anyway.
  - Every request path funnels through `_authorized_request`, which catches
    `httpx.HTTPError` and non-2xx statuses and re-raises as `RommError`
    with the status code and a body excerpt (capped at 300 chars). A raw
    `httpx.HTTPStatusError` (or any other httpx exception) never escapes
    the module — asserted directly in tests via
    `isinstance(exc, httpx.HTTPStatusError)` checks.
- **New:** `tests/test_romm_client.py` — 10 tests, all HTTP mocked via
  `httpx.MockTransport` (no live RomM required anywhere):
  1. `authenticate()` posts form-encoded and asserts the request
     `content-type` header is exactly `application/x-www-form-urlencoded`.
  2. a subsequent call (`list_platforms()`) carries `Authorization: Bearer
     tok-123`.
  3. `platform_id("dos")` resolves through `GET /api/platforms` and
     returns an `int`.
  4. `platform_id` caching — asserted on a request-count delta (not
     timing): calling `platform_id` three times total (including a
     *different* slug) after the first call adds zero further requests.
  5. `platform_id("nope")` raises `RommError` matching `"nope"`.
  6. a 401 from `/api/token` raises `RommError` matching `(?i)authenticat`
     and is explicitly asserted **not** to be an `httpx.HTTPStatusError`.
  7. a 500 from a regular authorized call raises `RommError` containing
     both the status code (`"500"`) and a body excerpt
     (`"internal server error"`), also asserted not to be
     `httpx.HTTPStatusError`.
  8. `ensure_collection` returns an existing id without issuing a `POST`.
  9. `ensure_collection` creates via `POST /api/collections` when no
     matching name exists.
  10. `add_to_collection` posts to `/api/collections/{id}/roms`.

No modifications to `src/romm_hub/sandbox.py`, `netpolicy.py`, or any
Task 1/2 file. `romm.install()`/seccomp is never touched by this task.

## Design notes / judgment calls (not fully pinned by the plan)

- The plan doesn't specify the exact JSON shape of `GET /api/platforms` or
  `/api/collections`. I assumed each platform dict has `id` (int) and
  `slug` (falling back to `fs_slug`) — consistent with `FetchPlan.platform`
  being described as a slug like `"dos"` elsewhere in the plan. This is
  mocked in tests, so it doesn't need to match RomM's live schema exactly;
  Task 4/7 consume only the resulting `int`.
- `ensure_collection`/`add_to_collection` wire formats (`{"name": ...}`,
  `{"rom_ids": [...]}`) are my own reasonable guess absent a captured
  fixture — not specified in Step 1's "at minimum" list, and there's no
  captured `openapi.json` in this worktree to check against. Flagging in
  case Task 7 or a later pass against the live RomM needs the field names
  adjusted.
