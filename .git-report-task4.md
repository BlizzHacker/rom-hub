# Task 4 report — chunked upload

## Update: two coordinator-flagged bugs fixed, post-review

The coordinator read RomM's actual source
(`rommapp/romm`, `backend/endpoints/roms/upload.py`) and found the
`{"id": ...}` guess was wrong, and — far more serious — a chunk-sizing
bug that mocked tests could not have caught because the mock accepted
any chunk length. Both fixed in commit (see bottom, this same branch):

1. **Response key**: `/start`'s real response is `{"upload_id":
   upload_id}`, not `{"id": ...}`. `upload_file` now reads
   `start["upload_id"]` and raises `RommError` naming the missing key
   plus the keys actually present if it's absent, *before* any chunk is
   attempted (test:
   `test_missing_upload_id_in_start_response_raises_clear_error`, which
   also asserts zero PUTs happen). Also noted: `upload_chunk`'s real
   response is `{"received": <int>, "total": <int>}` — `RommClient.upload_chunk`
   now returns the parsed JSON (was `None`) for a caller that wants it,
   though `upload_file` doesn't currently consume it.

2. **Chunk sizing (the important one)**: RomM's server does not trust
   the client's chosen `chunk_size` for each chunk's byte length. It
   derives its own expected size from the two headers already sent:
   `server_chunk_size = ceil(total_size / total_chunks)`, applied to
   every chunk except the last (which gets the remainder). My original
   code sliced with the *requested* `chunk_size` (8 MiB) directly, which
   only happens to match when `total_size` divides evenly by it — for a
   20 MiB file (`total_chunks=3`), the server expects
   6990507/6990507/6990506-byte chunks, not three ~8 MiB/~4 MiB chunks.
   Every uneven-division multi-chunk upload would have been rejected (or
   hung) against real RomM despite all 8 original tests passing.
   `upload_file` now computes `server_chunk_size = (total_size +
   total_chunks - 1) // total_chunks` right after choosing
   `total_chunks`, and reads/sends exactly that many bytes per chunk
   (remainder on the last), regardless of the caller's `chunk_size` hint
   (which only ever decided `total_chunks`).

3. **Mock hardening**: the shared `_handler()` in
   `tests/test_romm_upload.py` now captures `total_size`/`total_chunks`
   from the `/start` request's own headers and, on every PUT, recomputes
   `_expected_chunk_size` (a local copy of RomM's own formula) and
   returns a `400` if the body length doesn't match — instead of
   accepting any length unconditionally. **Verified this actually
   catches the bug**: I temporarily reverted `upload_file` to the old
   `fh.read(chunk_size)` behavior and reran the suite — 3 tests failed
   immediately with `RommError: PUT ... failed (400): {"detail":"chunk 0
   wrong size: expected 834, got 1000"}`, confirming the mock is a real
   contract check, not a rubber stamp. Restored the fix immediately
   after and reconfirmed green.

4. **New test**
   `test_uneven_division_sends_server_formula_sized_chunks` pins the
   coordinator's exact numbers: a 20 MiB file at the 8 MiB default chunk
   size sends chunks of `[6990507, 6990507, 6990506]` bytes, summing to
   the original size.

5. **`/complete` 409 "Missing chunks"`**: added
   `test_complete_409_missing_chunks_message_reaches_romm_error` —
   confirms this already worked with no code change needed. RomM's
   `_authorized_request` already funnels any non-2xx response body
   through `_excerpt(resp)` into the `RommError` message, so a `409`
   body of `{"detail": "Missing chunks: [0]"}` already surfaces the text
   "Missing chunks" in the raised error, unswallowed.

6. **413 note (per coordinator, not verified)**: the server also
   rejects with 413 if its derived chunk size exceeds
   `ROM_UPLOAD_MAX_CHUNK_SIZE`. That constant's value is unknown and not
   guessed here. Since a *larger* declared `total_chunks` yields a
   *smaller* derived `server_chunk_size`, if a 413 appears at Task 8's
   live run against real RomM, the fix is to lower `DEFAULT_CHUNK_SIZE`
   in `upload.py` (which raises `total_chunks` and thus lowers the
   per-chunk size RomM computes) — not a code-structure change.

## What changed

- **Modified `src/romm_hub/romm/client.py`** — added four methods to
  `RommClient`, all routed through the existing `_authorized_request`
  (so auth, token refresh, and non-2xx -> `RommError` conversion is
  shared with every other call the client makes, not reimplemented in
  `upload.py`):
  - `start_upload(platform_id, filename, total_size, total_chunks) -> dict`
    — `POST /api/roms/upload/start` with the four `x-upload-*` headers.
  - `upload_chunk(upload_id, index, chunk: bytes) -> None` — `PUT
    /api/roms/upload/{upload_id}` with `x-chunk-index` and the chunk
    bytes as the raw body.
  - `complete_upload(upload_id) -> dict` — `POST
    /api/roms/upload/{upload_id}/complete`.
  - `cancel_upload(upload_id) -> None` — `POST
    /api/roms/upload/{upload_id}/cancel`.
  - This was the gap Task 3's report flagged ("Task 4 will need
    RommClient to expose... the upload endpoints, or add its own
    methods") — resolved by extending the client rather than
    reimplementing HTTP/auth plumbing in `upload.py`.

- **New `src/romm_hub/romm/upload.py`** — `DEFAULT_CHUNK_SIZE = 8 *
  1024 * 1024` and `upload_file(client, path, platform_id,
  chunk_size=DEFAULT_CHUNK_SIZE, progress=None) -> dict`:
  - Rejects a zero-byte file with `RommError` naming the path, before
    any request is made (`total_chunks: 0` would hang the server).
  - `total_chunks = math.ceil(total_size / chunk_size)`.
  - Streams the file with `path.open("rb")` and `fh.read(chunk_size)`
    per iteration — never reads the whole file into memory.
  - Sends exactly `total_chunks` PUTs, indices `0..total_chunks-1`.
  - Wraps the chunk loop **and** the final `/complete` call in one
    `try/except Exception`: on any failure it calls `cancel_upload`
    (swallowing a `RommError` from cancel itself, so a failed cancel
    never masks the original error) and re-raises as `RommError`
    (re-raised as-is if it already is one, wrapped otherwise).
  - `progress(index_completed, total_chunks)` is called after each
    successful chunk PUT, if provided — not specified by the plan's
    Step 1 test list, added as a reasonable optional hook since
    `upload_file`'s signature includes it.

- **New `tests/test_romm_upload.py`** — 8 tests, all mocked via
  `httpx.MockTransport` (no live RomM anywhere), covering every plan
  bullet:
  1. A 20 MB file at the 8 MB default chunk size sends
     `x-upload-total-chunks: 3` and exactly 3 PUTs with `x-chunk-index`
     0, 1, 2.
  2. `x-upload-total-size` equals the real file size,
     `x-upload-filename` equals the file's name.
  3. Byte-for-byte reconstruction: a 2500-byte random file at
     `chunk_size=1000` (3 chunks), concatenated PUT bodies compared
     directly (`==`) and via `sha256` digest against the original.
  4. A 100-byte file at the 8 MB default chunk size sends
     `total_chunks: 1` and exactly one PUT.
  5. An empty file raises `RommError` matching `"empty"` and **zero**
     HTTP calls are made (`calls == []`).
  6. A chunk PUT failing (mocked 500 on chunk index 1) triggers exactly
     one `POST .../cancel` and raises `RommError`.
  7. A `/complete` failure (mocked 500) also triggers `/cancel` — not
     just mid-chunk failures.
  8. `x-upload-platform` is asserted to be the literal string of the
     integer id passed in (`"42"`), never a slug.

  Also asserted: `upload_file` returns the JSON body of the `/complete`
  response unchanged.

No modification to `src/romm_hub/sandbox.py`. `sandbox.install()` /
seccomp is never touched by this task — none of these tests spawn a
sandboxed subprocess.

## Design notes / judgment calls (not fully pinned by the plan)

- **Response body key for the upload session id**: the plan's
  "Verified API contract" table specifies headers and status codes for
  each step but not the JSON shape of the `/start` response. I assumed
  `{"id": "..."}`, matching the convention already used elsewhere in
  this client (`ensure_collection` reads `resp.json()["id"]`). This is
  fully mocked in tests, so it costs nothing now, but should be checked
  against the live `openapi.json` before Task 8's live end-to-end run —
  same category of risk Task 3's report flagged for `/api/collections`
  and was later corrected by the coordinator.
- Put the four new HTTP methods on `RommClient` rather than having
  `upload.py` build requests directly (e.g. via a raw `httpx.Client` or
  by reaching into `client._authorized_request` from outside the
  module). This keeps every RomM call — including uploads — going
  through the same auth/error-conversion path, and is what Task 3's
  report anticipated as the likely resolution.
- `progress` callback signature `(index_completed: int, total_chunks:
  int)` is my own choice; the plan doesn't test or specify it.
